# GPT6 Pro向け：闘技場の最強アルゴリズムを追求する実装指示書
対象：VOID PIT — UI仕様書つき闘技場。基準は同梱の `src/engine.js`、`src/data.json`、`src/arena/strategies.js`、`src/policies.js`、原作 `vendor/arena-cli/` とする。この文書は後続の改善作業への指示であり、現在の方針が数学的に最強だと主張するものではない。編集箇所と実装済み基盤の契約は `GPT6-Pro-arena-implementation.md` を参照する。
## 目的
既存5方針より、大会の生存率、金冠・銀杯を含む優勝実績、スコア、追加対戦の成績を改善する。ゲームの能力値や価格を有利に変えて勝率を上げてはならない。原作相当の操作から強い構成を作り、優勝した状態のままで対戦するという仕組みを維持する。
## 最初に読むもの
`src/engine.js` の `newRun`、`availableActions`、`validAction`、`fight`、`operation`、`stats`、`Session.restore` を読む。`src/arena/strategies.js` の `chooseBattleAction`、`chooseTournamentOperation` と、`src/policies.js` の `runTrial`、`opponentForecast`、`createDuel`、`duelForecast` を読み、現在の探索と対戦アダプターの制約を記録する。原作との比較は `tests/check.mjs` と `tests/oracle.cpp` の仕組みを使う。元仕様書は `docs/specification.md` とし、改善案を理由に原文を書き換えない。
## 絶対に維持するルール
初期HP96、MP32、SPD100、装備技3枠、全5戦、各試合20ラウンド、商品価格、習得候補、所有確認、装備確定時の計算、勝利後回復、金冠・銀杯の判定を維持する。戦闘の数値へ乱数を加えない。技、装備、敵のデータを書き換えない。BUG-01・BUG-02を含む原作の受理規則を、探索側だけで変更しない。
ただしユーザー指定の新版ルールとして、基本技waitは「めいそう」（MP消費0、HP+15・MP+6）、追加闘技場は双方HP・MP満タンで開始・再戦する。この現行ルールを改善の基準にする。方針版1.1、記録版VOID-PIT-WEB-2より前の成績を、そのまま新版の比較対象にしない。初期の回復技には癒しの雨・手当て・吸収のいずれかも入り、めいそうは常に使える。
大会生成の64bit LCGは `BigInt` のまま扱い、抽選順と抽選数を変えない。方針の探索や同点処理に乱数を使う場合は独立した状態を持たせる。大会seed、方針seed、方針ID、方針版、処理上限を記録する。演出、描画、説明文、音声の処理でゲームや方針の乱数を進めない。
SPDが高い側から実行し、同値ならプレイヤーが先行する。防御・魔法障壁の構えとrepriseの予約捕捉は行動順より前に処理する。Focus、Guard、Barrier、Burn、Bank、予約発動、休息、整数切り捨ては共通エンジンへ任せる。探索専用の簡易ダメージ関数を作って本番と分岐させない。
追加対戦の敵予告はプレイヤーがそのラウンドの行動を選ぶ前に確定する。確定した後で入力を盗み見て選び直さない。探索は観測可能な状態から行い、対戦アダプターの中で未選択のプレイヤー入力を実際の行動として扱わない。
## 改善の順序
まず既存方針の計測結果を固定し、改善前の比較対象として保存する。次に評価関数、行動探索、経路、習得、装備購入を別々に改善し、差分ごとに成績を比較する。同時に複数箇所を変え、どれが効いたか分からない変更にしない。
既存の技ランク優先型、相性重視型、生存優先型、短期先読み型、乱択試行型という5種類の性格は残す。共通の最適化を使ってもよいが、5つの名称だけを変えた同一方針へ統合しない。
## 戦闘探索
実際の合法手から子状態を作り、共通の `operation` を適用して評価する。発動・休息では `next` だけを展開する。無効手を「不利な有効手」として採点せず候補から除く。相手の既に確定した予告は初手の探索中に固定する。
手動入力で許される通常技の完全名を探索対象に含める案は、通常3枠内の案と別の実験条件にする。両方とも本編と同じ受理判定を使い、未装備quake・eclipse、MP不足、予約不在のrepriseを成功扱いしない。採用する行動集合を記録し、成績比較で混在させない。
評価は勝敗を最優先し、その後に優勝確率、残りHP・MP、スコア寄与、次の試合への余力を扱う。HP1の勝利と確定敗北を、見かけの与ダメージだけで逆転させない。途中の敵撃破を大会全体の優勝と同一視しない。次の画面が習得所や店へ変わる状態も正しく評価する。
Focusを維持して溜めを開始する、Burnとflareを組み合わせる、GuardでBankを貯める、相手の予約をcounterやrepriseで利用する、healing-rainで相手も回復する、といった複数ラウンドの費用と利益を評価する。MPの回復を得るために致死攻撃を受ける手や、残りラウンドで発動できない溜めを優先しない。
有限のビーム探索、反復深化、トランスポジション表、終盤の限定完全探索を候補とする。キャッシュキーには両者のHP・MP・上限・SPD・技枠・全状態・予約・敵予告・ラウンド・金冠監査に関係する履歴など、評価へ影響する値を含める。省いた状態で異なる局面を同一視しない。
対戦で相手の未来行動が未確定なら、固定仮定、複数応答、最悪応答など何を仮定したか明記する。仮想の応答を確定した本番予告へ上書きしない。手の選択後に相手がどう動いたかは、次ラウンドの観測として初めて利用する。
## 経路・習得・装備の探索
経路は目の前のHPだけで順位を付けず、現在の構成、相手SPD、技構成、将来の分岐、学べる技、残り体力とMPを評価する。ただし未公開の情報をUIより多く読む場合は、その情報条件を明示し、対人予告の先読みと混同しない。
習得所では、候補技を取るか見送るか、3枠のどこを交換するか、習得済み技を再装備するかを比較する。外した技を登録済み集合から削除しない。単独技ランクだけでなく、Focus、Burn、Bank、回復、相手の予告との組合せを評価する。
店では所持金、所有品、販売時期、防具1枠・装飾品1枠を守る。購入、所有品の装備、取り外し、何も買わず確定する選択も比較する。上限だけでなく確定後の現在HP・MPを `operation('leave-shop')` で得て評価する。未購入装備を試すシミュレーション結果は候補比較に限り、本番の所有品へ書き込まない。
## 計算量の上限
実時間だけを打ち切り条件にせず、再現可能な展開数・深さ・ロールアウト数で上限を固定する。初期候補は1判断あたり最大20,000状態展開、ビーム幅24、深さ6、乱択ロールアウト24本×最大8ラウンドとする。これらは上限であり、全方式で全部使う義務はない。安い確定手や単独合法手では探索を省く。
大会は最大512確定操作、追加対戦は20ラウンドとする。状態が進まない操作を検出し、上限到達、無効操作、通常敗北を異なる理由として記録する。上限到達を優勝へ変換したり、勝つまでseedを引き直したりしない。変更した上限は方針版とともに記録する。
Workerで予選を動かし、試行ごとに進捗を返す。キャンセルや停止要求を扱える境界を設ける。探索負荷を下げるときも、結果表示のために数値や勝者を捏造しない。
## 比較用seedと過学習対策
UIの本番予選は既存どおり共通seed1〜10、各方針10試行、合計50大会とする。この10個だけへの勝ち方の丸暗記を改善成果として扱わない。
改善実験では、学習・調整用seedを0〜255、検証用seedを256〜511、最終評価用seedを512〜1023とする案から始める。最終評価を見て調整した場合、その集合は最終評価用ではなくなるため、新しい未使用seed集合を確保する。加えてUINT64_MAX、上位bitだけが立つ値など64bitの境界seedを含める。seed集合をファイルへ固定し、比較対象すべてに同じものを渡す。
ランダム方針は同じ大会seedに複数の独立方針seedを与え、単発の幸運を除く。各条件の試行回数、方針seed生成式、引き分けの扱い、打ち切り件数を結果へ添付する。良かったseedだけ抜き出した平均を示さない。
## 評価指標
大会は優勝率を主指標とし、金冠率、銀杯率、敗退戦、20ラウンド敗北率、全試行スコア、優勝時HP・MP、使用ラウンド数、被ダメージ、処理時間、状態展開数を併記する。優勝者だけのHP平均と全試行の成績を混同しない。
追加対戦は既存5方針と改善方針の代表・他の優勝者を使い、同じ構成を双方HP・MP満タンにして総当たりする。プレイヤー側へ置いたときのSPD同値優先が成績へ影響するため、配置を入れ替えた結果も分けて報告する。旧版の残りHP・MPを引き継ぐルールの成績を、新版へ混ぜない。
集計値だけでなくseed単位の改善・同値・悪化件数を示す。勝率が同じならスコアや余力の改善を報告し、単一指標の改善をもって無条件に最強と呼ばない。優勝率が下がる変更を採用する場合は、そのトレードオフを明示して判断を求める。
## JavaScriptによる検証
検証の主経路はNode.jsのJavaScriptテストとする。ブラウザー操作、画面の文字列、見た目の勝利表示を、アルゴリズムが勝った証拠にしない。既存の `node tests/check.mjs` を基礎に、固定seedの評価スクリプト、回帰ケース、状態不変条件を追加する。既存の `build.sh` から必要な検証をまとめて実行できる構成にする。
原作比較が必要な環境では `bash arena/build.sh --verify` を使う。新しいテストが旧実装でも通るか、修正対象の欠陥を実際に検出するかを確認する。実装と同じ式を書き写しただけの自己一致テストにしない。
必須回帰ケースは、Focus付き攻撃と0ダメージ時の消費、GuardとBank上限、barrierとBurn付与、吸収の致死攻撃時回復、siphonの致死攻撃時MP回復省略、counterの実行時予約判定、repriseの入力時捕捉、溜め・発動・休息の履歴、無効入力で状態不変、監査直近6件、装備の乗算順と上限差分、20ラウンド制限である。
全優勝記録を `Session.restore(record)` へ渡し、優勝確定時の全状態と完全一致することを確認する。表示用の能力値だけを比較して済ませない。録画や画像の代わりに、失敗seed・方針seed・操作列・最初に不一致になった状態を保存する。
追加対戦開始前後で、両者のHP・MPが最大値へ回復し、上限・SPD・技枠・登録済み技・所有品が保存値と一致することを検証する。本編の元記録は書き換えず、再戦は同じ構成を再び満タンへ戻す。めいそうはHP+15・MP+6、上限、MP0時、先行致死時に不発、火傷継続、Focus維持を検証する。
予告確定後に異なるプレイヤー入力候補を検査しても、確定済み予告が変わらないことをテストする。探索が元状態や共有配列を書き換えないこと、同じseed・方針版・操作列から同じ結果になること、大会LCG状態が方針の展開数で変わらないことを確認する。
## 採用ゲート
共通エンジンとデータに無関係な変更がなく、原作比較と回帰テストが成功していること。固定した評価集合で旧版と比較し、失敗・打ち切りを隠さず報告していること。全優勝者の再生と対戦スナップショット一致が成功していること。全判断と大会に有限上限があり、処理量と実測時間が記録されていること。UI予選の試行数と勝者登録条件を守っていること。
## 納品
変更した方針コード、方針版、JavaScriptテスト、seed集合、評価実行コマンド、旧版との比較JSONまたはCSV、再現可能な代表操作記録、改善内容と残る弱点の説明を渡す。結果表には実行環境、実行日、試行数、各上限を添える。未実行の検証を成功と書かない。最強という表現を使う場合は、比較対象・情報条件・評価集合・予算の範囲を必ず併記する。
